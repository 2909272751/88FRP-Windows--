# 88FRP Node 开发设计（3.3.0）

## 1. 项目定位

本项目保留三种运行入口：

- Windows 原生客户端：当前主线。用 WPF 管理一台固定设备，提供一个统一公网入口。
- CLI / 本地 agent：保留原有交互菜单、常驻后台和实例管理能力。
- Docker Web：保留多实例管理能力，并使用同一套 Node 核心和数据结构。

3.3.0 的重点不是删除旧能力，而是在 Windows 端增加“一台设备一个 App”的统一入口。旧实例、账号、隧道选择、分组和旧版访问中心继续保留，避免升级时破坏已有配置。

## 2. 总体架构

```text
Windows 桌面端（WPF）
  -> 127.0.0.1:8801（仅本机管理 API / 页面）
  -> Node Web 核心
       -> GatewayService
          -> CaddyManager       HTTPS、通配证书、按 Host 路由
          -> FrpcManager        IPv4 兜底和 SSH/UDP 公网映射
          -> RelayManager       本机 TCP/UDP 双栈端口汇合
          -> CloudflareDns      A/AAAA 四记录同步与账本
          -> Ipv6Provider       本机公网 IPv6 检测
          -> FirewallService    受管 Windows 防火墙规则
          -> GatewayStore       原子状态、审计和运行日志

IPv6 客户端 -> 设备公网 IPv6:7777 -> Caddy -> 127.0.0.1:<服务端口>
IPv4 客户端 -> 88FRP 节点 IPv4:7777 -> frpc -> 127.0.0.1:7777 -> Caddy
```

统一入口的 Caddy 与 frpc 都是受管子进程。网页服务新增、删除或修改时只生成新 Caddy 配置并重载 Caddy；只有公网端口、SSH 或 UDP 映射变化时才重新生成并重启统一 frpc。

## 3. 端口与地址模型

| 端口/地址 | 默认值 | 说明 |
| --- | --- | --- |
| 本机管理端口 | `8801` | 只监听 `127.0.0.1`，供 WPF 和本机浏览器使用 |
| 统一入口端口 | `7777` | Caddy 双栈监听，公网 IPv6 和 88FRP IPv4 都回源到这里 |
| 服务本地端口 | 由用户填写 | Caddy 按子域名转发到 `localHost:localPort` |
| SSH 公网端口 | 由用户填写 | 同一端口支持 IPv6 直连和 IPv4 兜底 |
| UDP 公网端口 | 每个服务独立 | 同一端口支持 IPv6 直连和 IPv4 兜底 |

统一入口域名只负责解析到设备或 88FRP 节点，不携带端口。浏览器和 SSH 客户端必须使用实际的统一入口端口；端口设置为 `443` 时可以省略。同一 88FRP 服务器上的多台设备不能同时占用同一个公网端口，必须为每台设备分配不同的统一入口端口。

## 4. 核心模块

### 4.1 GatewayStore

负责：

- `gateway/state.json`：设备、服务、Cloudflare 账本、SSH 和调度设置
- `gateway/runtime.json`：Caddy/frpc 进程状态和调度检查结果
- `gateway/Caddyfile`、`gateway/frpc.toml`：当前运行配置
- `gateway/audit.log`：结构化审计日志
- `gateway/logs/`：Caddy、Caddy 访问和 frpc 输出

状态、运行状态和配置均使用临时文件、刷盘、校验和原子替换；保留 `.previous` 备份。读取损坏状态时尝试备份恢复，不把空配置写回。

### 4.2 GatewayModel

集中实现：

- 设备域名、服务子域名、本地地址和端口校验
- Caddyfile 生成
- 统一 frpc 配置生成
- A/AAAA 期望记录生成
- SSH/UDP 显示地址生成
- 敏感字段脱敏

子域名只允许小写字母、数字和连字符；`admin`、`root`、`portal`、`www` 为保留名称。网页服务不能反向代理到统一入口或本机管理端口，避免回环。

### 4.3 GatewayService

作为统一入口编排层，负责：

- 初始化、从旧实例迁移或从同步密钥创建来源
- 服务与 SSH 设置变更
- Caddy/frpc 应用、验证、回滚和启动
- Cloudflare Token 验证和定时 DNS 同步
- IPv6/IPv4 目标检测和状态汇总
- 防火墙开放
- 运行日志读取
- 开机恢复、进程守护和安全停止

任何一次应用变更都先保存旧状态和旧配置；新配置验证或进程启动失败时恢复旧状态、旧配置和旧进程，并写审计记录。

### 4.4 CloudflareDns

使用 Zone 级 API Token，维护：

- `<设备根域>` A -> 88FRP 节点 IPv4
- `<设备根域>` AAAA -> 设备公网 IPv6
- `*.<设备根域>` A -> 88FRP 节点 IPv4
- `*.<设备根域>` AAAA -> 设备公网 IPv6

记录为 DNS-only（灰云），不使用 Cloudflare 代理，以保留真实客户端地址并让 Caddy 自己处理 TLS。证书使用 Cloudflare DNS-01 通配证书。

DNS 同步规则：

1. 地址、域名或 zone 未变化时只更新时间状态，不调用写入 API。
2. 地址变化时先找本工具精确备注和本机账本中的记录，再更新或创建。
3. 不覆盖手工 A、AAAA、CNAME；TXT 可以共存。
4. 删除只允许同时满足本机账本、精确托管备注、类型和域名范围匹配。
5. 失败时保留旧目标并退避重试；下一次成功同步会修复旧账本。

### 4.5 CaddyManager

Caddy 版本和插件在构建脚本中固定：

- Caddy `v2.11.9`
- `caddy-dns/cloudflare v0.2.4`
- xcaddy `v0.4.7`
- Go `1.26.0`

应用新配置前先执行 `caddy adapt` 做离线预检，不访问 Cloudflare。配置成功后重载；重载或启动失败时恢复旧 Caddyfile。代理时删除外部伪造的 `X-88FRP-Desktop` 头，并补充真实来源地址。

### 4.6 FrpcManager

统一 frpc 始终包含一条网页入口映射：

```text
remotePort = 设备统一入口端口
localPort  = 设备统一入口端口
```

另外按需添加 SSH 和 UDP 映射。frpc 配置包含鉴权，属于私密文件。新配置应用失败时恢复 `.previous` 并重启旧配置；后台守护会检测异常退出并恢复。

### 4.7 RelayManager

SSH/UDP 的公网端口和本地端口不同时，通过本机同端口中继汇合两条路径：

- 公网 IPv6 监听 -> 真实 `localHost:localPort`
- `127.0.0.1:<publicPort>`（由 frpc 回源）-> 真实 `localHost:localPort`

停止中继时主动断开活跃 TCP 连接并关闭 UDP socket，避免长连接导致后台退出卡住。端口相同时尽量复用应用自身监听。

### 4.8 Ipv6Provider

只接受全球单播 IPv6（`2000::/3`），排除回环、链路本地、ULA 和未指定地址。优先选择稳定地址和合适接口；支持自动检测和手动指定。检测结果每次调度都参与比较，变化后才更新 AAAA。

### 4.9 FirewallService

只管理受管入站规则：

- TCP：统一入口端口，以及启用 SSH 时的 SSH 公网端口
- UDP：所有启用的 UDP 公网端口
- 不关闭 Windows 防火墙，不删除其他程序规则

### 4.10 ManagedProcess

统一管理 Caddy、frpc 和中继的生命周期：

- 记录 PID、启动时间和进程所有者
- 检测崩溃并重启
- 避免 PID 复用误杀
- 跨重启接管旧版受管进程
- 停止时先优雅退出，超时再安全清理

## 5. 生命周期

### 5.1 启动

1. 初始化数据目录和锁。
2. 读取网关状态；损坏时尝试 `.previous` 恢复。
3. 已初始化则清理旧实例和旧访问中心，启动统一入口。
4. 未初始化则恢复旧实例/访问中心，保持旧版兼容流程。
5. 启动 Caddy、frpc 和所需中继，启动 DNS 调度器。

### 5.2 定时调度

默认每 5 秒：

- 检测本机公网 IPv6
- 解析 88FRP 节点 IPv4
- 比较域名、IPv6、节点 IPv4 和 zone
- 只在目标变化或手动同步时访问 Cloudflare
- 守护 Caddy、frpc 和中继
- 写运行状态和必要的审计

失败使用退避，不在每个 tick 中重复打爆远程接口。

### 5.3 停止

停止调度器 -> 停止受管中继和进程 -> 释放后台锁 -> 关闭 Web 监听和长连接。重启后台时保留实例恢复意图，避免“重启后台”被误认为用户要永久停止服务。

## 6. 安全边界

- 管理 API 默认需要控制台登录；`127.0.0.1` 且带本机桌面标记的请求才可直接进入。
- Caddy 在公网代理时强制删除外部传入的 `X-88FRP-Desktop`，不能靠伪造请求头绕过登录。
- 公开导航 API 只读，不返回凭据、账本或私密配置；管理页不公开。
- Cloudflare Token、FRP 密钥和账号密码使用本机 DPAPI 加密保存。
- 审计和进程日志对常见 Token、密码、Authorization 模式脱敏。
- `gateway/frpc.toml` 和整个数据目录仍视为私密数据，不能提交或上传。
- Windows 防火墙只开必要端口；公网访问还需要光猫/路由器和服务端放行。

## 7. 持久化与回滚

| 文件 | 备份 | 回滚目的 |
| --- | --- | --- |
| `gateway/state.json` | `.previous` | 恢复设备、服务和 DNS 账本 |
| `gateway/runtime.json` | `.previous` | 恢复运行状态显示 |
| `gateway/Caddyfile` | `.previous` | 恢复上一次可用路由 |
| `gateway/frpc.toml` | `.previous` | 恢复上一次可用映射 |

进程启动失败时：

1. 恢复旧状态。
2. 恢复旧 Caddyfile/frpc.toml。
3. 重新应用旧进程。
4. 写入 `caddy.rollback`、`frpc.rollback` 或 `gateway.rollback.*` 审计。

源码层面的回滚按 `docs/变更溯源-20261122.md` 中列出的文件范围执行，不能用删除数据目录代替回滚。

## 8. 旧版兼容架构

以下旧能力仍存在：

- CLI 菜单和子命令
- 本地 agent 常驻
- 多实例 `instances.json`
- 88FRP 配置同步、隧道选择和分组
- 旧版域名绑定
- 独立访问中心
- Docker 多实例 Web

统一入口初始化后，Windows 默认进入单设备模式；旧版兼容页仍可打开。原有数据不会被自动合并、覆盖或删除。

## 9. 构建与验证

```powershell
npm test
npm run build:web:single
npm run build:windows:native
npm run build:windows:installer
```

`build:windows:native` 会在缺少 `bin/amd64/caddy.exe` 时调用固定版本构建脚本。Caddy 二进制是构建产物，不纳入 Git，但会进入便携包和安装器。

测试必须串行运行。Windows 上并行的磁盘 I/O 会让访问中心相关测试超时，不代表生产逻辑失败。

## 10. 已知边界与后续约定

- 当前统一入口主要覆盖 HTTP 网页、SSH 和 UDP；其他 TCP 协议继续走旧版实例或单独映射。
- 统一入口依赖 Cloudflare DNS 和 88FRP 节点；没有可用 Token 或来源配置时只能本机访问。
- 公网 IPv6 检测依赖网卡和系统命令，地址变化存在检测间隔。
- 5 秒是检查间隔，DNS TTL 和客户端缓存决定实际生效速度。
- 当前安装包未做商业代码签名，Windows 可能显示未知发布者。
- 任何影响运行行为的改动，必须在 `docs/变更溯源-<日期>.md` 追加原因、文件、验证和回滚，不得写入真实凭据。
